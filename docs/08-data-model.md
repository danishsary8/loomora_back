# Loomora: Data Model and Rules (A6, v1.0)

Database: PostgreSQL (Neon). All primary keys are **UUIDs generated by the client or server**, so guest data can move into an account without id clashes. All timestamps are stored in UTC. "Today" is always computed in the **user's own time zone** (users.timezone, an IANA name such as Asia/Phnom_Penh).

## Tables
**users**: id, name, email (unique), password (nullable for Google users), google_id (nullable, unique), email_verified_at, timezone, goal (be_consistent | manage_time | finish_tasks | other, nullable), heard_from (text, nullable), survey_done (bool), current_streak, longest_streak, last_streak_date, time_format (12h | 24h, default 24h), week_starts_on (1 to 7, 1 = Monday, default 1), google_exchange_digest (nullable, unique) and google_exchange_expires_at (nullable) for the short-lived Google sign-in exchange, created_at, updated_at. The API's `has_password` is derived from password being set; it is not a column.

**todos**: id, user_id, title (max 200), category (study | work | health | life | rest | other), due_date (date, nullable), done_at (timestamp, nullable), created_at, updated_at.
R2 adds: notes (max 2000, nullable), priority (low | normal | high, default normal), parent_id (nullable, a top-level to-do of the same user; deleting the parent cascades), repeat_rule (jsonb, nullable), next_todo_id (nullable, the repeat successor; set to null when that to-do is removed), remind_at and remind_dismissed_at (UTC, nullable), deleted_at (soft delete).

**daily_intentions**: id, user_id, local_date (date), text (max 200), created_at, updated_at. Unique (user_id, local_date).

**focus_sessions**: id, user_id, mode (countdown | stopwatch), end_reason (completed | ended_early), started_at and ended_at (UTC, millisecond precision, ended_at on or after started_at), local_date (date), planned_focus_ms (nullable), focus_ms (greater than 0), break_ms and paused_ms (0 or more), todo_id and schedule_item_id (both nullable, at most one set, each set to null when that item is removed), label (max 200, nullable), segments (jsonb), laps (jsonb, nullable), payload_hash, created_at, updated_at, deleted_at (UTC, millisecond precision, soft delete).

**notes**: id, user_id, schedule_item_id (nullable, set to null when the schedule item is deleted), local_date (date, nullable; an occurrence of that block, returned only while schedule_item_id is set), title (max 120, nullable), body (max 10000, nullable), revision (integer, at least 1, default 1, set only by the server; B-053), created_at, updated_at, deleted_at (soft delete). A note needs a title or a body.

**schedule_items**: id, user_id, title, category, start_time (time), end_time (time), days (smallint[] of 0 to 6, 0 = Monday), starts_on (date), ends_on (date, nullable), created_at, updated_at.

**schedule_exceptions**: id, schedule_item_id, date, type (skip | override), title (nullable), start_time (nullable), end_time (nullable). Unique (schedule_item_id, date).

**schedule_checkins**: id, schedule_item_id, date, done_at. Unique (schedule_item_id, date).

**feedback**: id, user_id (nullable), message, created_at.

Laravel Sanctum adds personal_access_tokens. A password_reset_tokens table is also needed.

## Business rules
1. **Today list** = to-dos with due_date = today, to-dos with no due date that are not done, and Overdue to-dos. Items with due_date in the future are hidden until their day.
2. **Overdue** is computed, not stored: due_date < today (user time zone) and done_at is null. It carries over automatically, with no scheduled job. Overdue items older than 30 days still show but are marked "Old".
3. **To-do default due date** is today when created from the Today screen.
4. **Schedule occurrence on a date D**: the item occurs if D is on or after starts_on, on or before ends_on (if set), and weekday(D) is in days. Then apply exceptions: skip removes it, override replaces title or times for that date only.
5. **"Only today"** edit creates an exception (override) for that date. **"All repeats"** edits the schedule_item itself. **Delete "only today"** creates a skip exception. **Delete all** removes the item and its exceptions and check-ins.
6. **Now / Next**: Now is the occurrence whose start <= current local time < end. Next is the first occurrence starting later today. If none, Now shows "Free" and Next shows "Nothing more today".
7. **Check-off**: a to-do is done when done_at is set (toggle clears it). A schedule occurrence is done when a schedule_checkins row exists for that date.
8. **Streak**: a local day counts if at least 1 to-do or schedule occurrence was checked off that day. A day with nothing planned (no to-dos due and no schedule occurrences) is skipped and never breaks the streak. A planned day with zero check-offs breaks it, but today is never judged until it ends. The server stores current_streak, longest_streak and last_streak_date and recomputes them lazily on check-off and on app open.
9. **Guest to account migration**: the client sends the guest to-dos, schedule items, exceptions, check-ins, daily intentions, finished non-deleted Focus sessions and notes through the import call, in bounded chunks when the plan is larger than one request allows (per-request limits are in `openapi.yaml`). Rows keep their client UUIDs. A subtask, repeat successor, exception, check-in, Focus session link or note block must point at a row the user already has or one in the same request. A row the user already has is skipped and never overwritten (same id, deleted to-dos, Focus sessions and notes included; same item and date for exceptions and check-ins; same date for daily intentions), so re-sending a chunk creates no duplicates; for each skipped note the response reports `identical`, `different` or `deleted` (B-052). A UUID that belongs to another account rejects the request (422, or 409 for a Focus session). Each request runs in one database transaction: if it fails, nothing from that request is written, and chunks that already succeeded stay committed. The guest data stays on the device until every chunk succeeds and the client has verified the outcome; a successful response alone does not prove a skipped note matches the guest copy, so the client keeps the guest plan whenever a skipped note is `different` or `deleted`, or cannot be verified.
10. **Delete account** removes the user and all their rows immediately (cascade).
11. **Validation**: title 1 to 200 characters; start_time < end_time; days not empty; at most 500 to-dos and 100 schedule items per user (R1 limits). Repeat successors and their subtasks do not count toward the 500 to-dos, on check-off or on import (DECISIONS I5, I9).
12. **Categories** are a fixed set of 6 (string enum), not a table.

13. **Focus sessions**: deleting a finished session (B-046) stamps deleted_at and hides it from ordinary reads. Restore clears the stamp if fewer than seven days elapsed, otherwise 410. Recording retries compare the original row, including deleted rows: an identical retry succeeds and a changed payload is a conflict. Removing a linked to-do or schedule item does not delete its session.
14. **Notes**: deleting a note soft-deletes it and hides it from ordinary reads. Restore within seven days returns it, otherwise 410. Deleting a schedule block keeps its notes as standalone notes. Editing never changes another user's note (404).
16. **Note revisions** (B-053): a note starts at revision 1, also when imported, and a client value is ignored. The revision goes up by one, in the same transaction, on an edit that changes a field, a delete, a restore of a deleted note, and a schedule block delete that detaches the note (deleted notes included; the block and occurrence date are cleared). An edit that changes nothing keeps the revision. An edit or delete may carry `expected_revision`: a different current revision is a 409 with nothing written; without it the write applies as before. Deleting an already deleted note is still a 204. Creating with a UUID the user already has returns 200 and the stored note only when it is active and its visible fields match; otherwise 409, and a deleted note stays deleted. Import never changes an existing note (rule 9).
15. **Delete account** (rule 10) also removes every daily intention, Focus session and note, including deleted ones.
