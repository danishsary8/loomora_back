# B-034 Google-only account deletion design

**Proposed for planner review · Q23 open · 20 November 2026**

The product includes Google accounts and account deletion. S14 requires confirmation followed by immediate deletion. QA-001 found that the profile blocks Google-only deletion while the frontend API summary promises Google confirmation. QA-004 also requires customer-facing privacy and terms to reflect actual cloud processing, retention, contact details and deletion availability. This proposal is based on backend `v2-rebuild` at `bb19bc0` and frontend source at `05362fda`. [Feature list](02-feature-list.md) · [Product decisions](07-project-decisions.md) · [QA-001 / QA-004 follow-up](PROGRESS.md#2026-11-20-b-032-staging-integration-and-release-readiness)

## Current behavior

- `DELETE /api/v1/me` passes through `auth:sanctum` and the signed-in rate limit. `DeleteMeRequest` requires a nonempty `password` string. An omitted password gets a required-field 422. A supplied password for a user whose stored password is null gets a 422 on `password` before `MeController::destroy` runs. A configured password, including on a Google-linked account, is checked with `Hash::check`. The bearer supplies the account identity. An input `user_id` cannot select another account. [Routes](../routes/api.php) · [Request](../app/Http/Requests/Account/DeleteMeRequest.php) · [OpenAPI](openapi.yaml)
- `UserResource` derives `has_password` from `password !== null`. `google_id` is private. Google signup creates a verified user with no password. The Socialite login callback uses expiring encrypted state with `stateless()` and `prompt=select_account`, looks up by `google_id` and falls back to email, and may create or link the user. Its cached exchange code issues a 30-day Sanctum bearer. This flow checks provider identity for login and has no Google authentication-time check. Its sequential `Cache::pull` replay test establishes sequential use only. [User resource](../app/Http/Resources/UserResource.php) · [Google login](../app/Http/Controllers/Api/V1/GoogleAuthController.php) · [Token response](../app/Http/Controllers/Concerns/RespondsWithToken.php)
- For password deletion, `User::deleteWithData()` runs in one transaction. It removes all Sanctum tokens, password-reset rows for the account email and database sessions, then deletes the user. Foreign keys cascade to owned to-dos (including soft-deleted rows and subtasks), schedules with exceptions and check-ins, daily intentions, and user-linked feedback. A cancelled delete throws and rolls back cleanup. The controller returns an empty 204 after the transaction. The tests exercise real bearer revocation, isolation of another user, and rollback. [User model](../app/Models/User.php) · [Account tests](../tests/Feature/FeedbackAndAccountTest.php)
- The frontend `DeleteAccountSheet` displays a current-password form for `has_password: true`, a restriction message for `false`, and refreshes unknown legacy capability through `GET /me`. `authApi.deleteMe` sends `{password}` and requires 204. It preserves the session on errors and only signs out the original session on success. The frontend API summary still promises Google confirmation. Keep this mismatch visible under Q23 and align frontend docs and disclosures with the planner's launch decision. [Frontend profile at assessed SHA](https://github.com/danishsary8/Loomora_front/blob/05362fda2c7948a5f4f68a8cc5a652336fb8d053/src/features/profile/DeleteAccountSheet.tsx) · [Frontend API summary](https://github.com/danishsary8/Loomora_front/blob/05362fda2c7948a5f4f68a8cc5a652336fb8d053/docs/09-api-design.md)

## Options for Q23

| Consideration | A · Google reauthentication | B · Verified email confirmation | C · Restrict Google-only signup at launch |
| --- | --- | --- | --- |
| Identity and freshness | Signed Google `sub` matches the stored `google_id`, and signed `auth_time` proves recent Google authentication. A challenge-bound assertion and final Loomora confirmation establish purpose and intent. Google cannot force a fresh prompt from our app. | A new message proves present access to the stored, verified mailbox. Inbox compromise, forwarding, shared access, and mail delivery weaken assurance. An existing `email_verified_at` proves a historical check. | The password check continues to prove possession of the current Loomora password. Google-only deletion remains unavailable, including for existing Google-only users. |
| Ownership and account switching | Bind to authenticated user, initiating Sanctum token, tab, purpose, and stored Google subject. Reject a different returned subject even if emails match. | Send only to the principal's current verified address. Bind redemption to user, token, purpose and the verified address snapshot. Recheck the address and credential state. No account selection or target address input. | Enforce the signup gate server-side at both redirect creation and callback, including already-issued signup state. Permit existing sign-in only by a previously linked Google subject if the planner keeps existing Google access. Preserve the password path for linked password accounts. |
| Expiry, replay and browser risks | One-time state, OIDC nonce, S256 PKCE and the initiating tab's secret. Fixed origins and callback. Single-use confirmation committed with deletion. | A separate high-entropy random token, digest stored, 10-minute lifetime, superseded on resend. Prefer a pasted code in the authenticated sheet to keep it out of URL logs, history, referrers and link scanners. Never delete from a link or GET. Keep confirmation in POST or DELETE JSON and redact it from logs. Consume in the same transaction as deletion. | No new proof, expiry, redirect or CSRF surface for deletion. Retain normal OAuth protections for any existing sign-in. Test stale signup state and direct API callers. |
| Rate limits and disclosure | Limit starts, redemption and final attempts per account and IP. Use generic validation errors for failed proofs. Redact codes and claims. | Cap sends per account and IP (start with three per account per 10 minutes) and verification attempts (five per account per 10 minutes, with an IP cap). Use generic responses and never accept or expose another user's address. Redact delivery and verification logs. | Keep existing auth and API limits. Return a consistent signup-unavailable response regardless of supplied identity. Keep availability clear in the UI. |
| Concurrency and data integrity | One active row per user, atomic verification and deletion under account lock. Transactionally reuse the existing cascade and all-token revocation. Roll back proof consumption and cleanup together. | Same account locking, rollback, cleanup and revocation as A. Atomically supersede old confirmations and treat failed sends as unusable. Verify expiry and mailbox binding inside the transaction. Concurrent redemption succeeds at most once. | No Google deletion writes or revocation. Retain current password rollback and cascade. Guard the creation point so concurrent callbacks cannot create a Google-only user under the restriction. |
| Compatibility, frontend and testing | Separate deletion OAuth from login, signup and account linking. Passwords take precedence even on Google-linked users. Requires a callback, accessible new confirmation states, provider fakes, PostgreSQL race tests and controlled staged freshness tests. | Reuse only the canonical origin and mail infrastructure. The current verification HMAC of user ID, email and expiry is repeatable until expiry and the public endpoint only verifies email. Requires an independent mail template, confirmed delivery, a code-entry UI and tests for replay, scanners, rollback and wrong mailbox/session. | Hide Google signup across signup and guest migration entry points. Reflect the restriction in Profile, API summary, privacy and terms. Cover old-client, deep-link and server rejection behavior. The planner must decide what to tell existing Google-only users about their deletion options. |

**Recommendation.** Approve A for implementation with a provider capability gate. It relies on the Google identity already linked to the account, avoids mailbox-only proof, and keeps password confirmation for users who have a password. Build against a verified Google configuration that supplies signed `auth_time`. Demonstrate that a stale Google session fails and that deliberately signing in again at Google lets the user finish with the linked identity. Google documents that callers cannot request Google Account reauthentication. Account selection, consent and token issuance time alone give no proof of recent authentication. If the gate fails or the planner requires a forced credential prompt, choose C for public launch. B would require a separate planner decision accepting the weaker mailbox assurance. [Google session-age requirements](https://developers.google.com/identity/siwg/security-bundle) · [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect) · [NIST email authentication guidance](https://pages.nist.gov/800-63-4/sp800-63b.html#out-of-band)

The current password broker looks up users by email and can populate a null password after a valid reset. Treat this as existing recovery behavior. A deletion flow must not silently enroll a password, trigger reset, change email or link a Google identity. [Password reset controller](../app/Http/Controllers/Api/V1/PasswordResetController.php) · [Email verification](../app/Services/EmailVerification.php)

## Proposed Option A contract

All API paths below are relative to `/api/v1`. The start and verify endpoints and the Google branch of delete require a real, unexpired Sanctum personal access token in `Authorization: Bearer`, the allowed frontend origin, and JSON. The authenticated subject determines ownership. Keep the same initiating token through verification and deletion. CORS stays credential-free. These Google operations do not mint an API token. The design follows the `{data: ...}` resource envelope, leaves login/register at `{token, expires_at, user}`, and uses Laravel `{message, errors: {field: [message]}}` for 422s.

| Operation | Request | Success |
| --- | --- | --- |
| `POST /me/deletion/google/challenge` | `{ "browser_challenge": "<base64url SHA-256 of the tab's browser_verifier string>" }`. The tab generates 32 random bytes and encodes them as unpadded base64url for `browser_verifier`. | `201` with `{ "data": { "id": "<uuid>", "authorization_url": "<Google HTTPS URL>", "expires_at": "<UTC ISO 8601>" } }`. The URL has a dedicated callback URI derived from the canonical frontend origin. A new challenge supersedes previous attempts for the user. |
| `POST /me/deletion/google/verify` | `{ "challenge_id": "<uuid>", "code": "<Google authorization code>", "state": "<returned state>", "browser_verifier": "<tab secret>" }` | `200` with `{ "data": { "id": "<uuid>", "expires_at": "<UTC ISO 8601 confirmation expiry>" } }`. The same challenge becomes confirmed. The browser can now offer the explicit destructive action. |
| `DELETE /me` | Existing `{ "password": "<current password>" }` for anyone with a password. For Google-only accounts, `{ "google_confirmation": { "challenge_id": "<uuid>", "browser_verifier": "<tab secret>" } }`. Accept just one method. | `204`, empty body, only after deleting the user and owned data and revoking all Loomora credentials in the database transaction. |

**Error handling.** Return `401 {"message":"Unauthenticated."}` for unset, invalid, expired or revoked credentials, including a token that disappeared while the request waited for an account lock. Reject missing or mismatched `Origin` on the Google operations with generic 403 and an unsupported content type with 415. Use 422 for malformed inputs and incompatible methods. Put well-formed but invalid, stale, expired, revoked, used, superseded or cross-account proofs under one generic `errors.google_confirmation` response. Keep `errors.password` for missing or wrong passwords in existing clients and reject a password-only request from a Google-only user. The Google endpoints expose no public lookup or distinct provider/account-match details. Return 429 with `Retry-After` on limits, 503 with a generic message for a disabled provider capability or provider outage, and a sanitized 500 on unexpected deletion failure.

**Rate limits.** Start with three challenge creations per account and ten per IP per 10 minutes. Limit verification and Google final submissions independently to five attempts per account and 30 per IP per 10 minutes. Keep the existing API throttle and password behavior. Apply the deletion limits before provider calls or destructive work, using shared counters across API workers and Q25's trustworthy ingress IP. Return fixed errors without echoing proof material.

### Proof and transaction

1. Under the user-row lock, confirm that the bearer still exists and belongs to the same user, has not expired, and the user has `password = null` and a linked `google_id`. Create a five-minute challenge bound to the user's UUID, bearer token row ID, Google subject, tab verifier digest and deletion purpose. Use independently generated high-entropy state, nonce and server-side PKCE verifier. Persist state and nonce digests and encrypt the PKCE verifier at rest. Send Google a code-flow request with `openid`, a random state and nonce, S256 PKCE, the exact registered redirect URI and essential `auth_time`. Use `prompt=select_account` for account selection only. Use the environment's configured Google client, request online access, and discard provider access tokens after verification. [Google discovery metadata](https://accounts.google.com/.well-known/openid-configuration) · [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html)
2. Receive Google's authorization code on the fixed frontend `/auth/google/deletion/callback` route. The frontend scrubs the callback URL and posts only after recovering the initiating tab's verifier and original Loomora account context. The API checks the current account, token, state, tab digest, purpose, expiry and pending state. Atomically reserve the attempt and consume state before exchanging the code server-to-server. A duplicate verification loses the reservation. On provider failure or a stale claim, invalidate the attempt and let the user start again. A crashed reservation expires. Keep network calls outside database locks and recheck the reservation and all bindings before persisting confirmation.
3. Verify the returned ID token with a maintained verifier and Google's JWKS. Validate signature/algorithm, Google issuer, exact configured audience and authorized party when present, issuance/expiry, nonce and case-sensitive `sub == google_id`. Require numeric signed `auth_time` in the last five minutes, with at most 30 seconds of skew for future time and consistency with `iat`. `iat`, consent, `login_hint`, email and the login access token cannot establish this freshness or linkage. Missing or stale claims fail closed. Use `min(challenge expiry, verified time + 120 seconds, auth_time + 300 seconds, ID token expiry)` as the confirmation expiry. Persist only the proof metadata required for final validation. [Google ID token claims](https://developers.google.com/identity/openid-connect/reference) · [Google session age](https://developers.google.com/identity/siwg/security-bundle#authentication-time)
4. At final submit, lock the same user first, then recheck and lock the bearer and confirmation in that order. Require an unexpired confirmed row bound to the same user, token, tab and current Google subject. Recheck that the password is still null. Mark the confirmation consumed and call the existing deletion cleanup in one database transaction. Account deletion cascades through challenge rows. If cleanup fails, the transaction restores the proof and all related rows and a user may retry until the original expiry. Parallel final submits produce at most one 204. The loser gets 401 if its bearer was removed or 422 if its proof was superseded while the account remains. Require issuance of tokens for existing users, password reset, and Google linkage writes to serialize on this same user row and recheck existence/current credentials before writing. This prevents a pending sign-in exchange from creating an orphan token after cleanup. Keep both deletion methods on the same cleanup and locking path.

### Data model and rollout

Add a deletion-challenge table on the primary database with UUID primary key, unique cascading `user_id`, initiating `personal_access_token_id`, Google subject snapshot, state/nonce and tab-verifier digests, encrypted PKCE verifier, state (`pending`, `verifying`, `confirmed`, `consumed`, `failed`), creation/expiry and verified/confirmation-expiry timestamps. Add an expiry index and prune expired rows. Scope all lookups to the locked user and expected challenge ID. Omit raw bearer tokens, provider codes and ID tokens from storage. Remove transient PKCE material after exchange. Expiry limits validity even when cleanup is delayed. `users` and the authentication response need no new fields or account backfill. Use one additive migration and gate exposure until the paired frontend, registered callback and claim settings are verified. With the Google flow disabled, new attempts fail safely and the existing password contract is available.

### Frontend integration

1. Keep the legacy `GET /me` capability lookup and existing password form. For an eligible Google-only session, show the existing deletion warning and an explicit action to verify with Google. Save the challenge ID, starting user ID and short-lived tab verifier in `sessionStorage` for the round trip. Generate the verifier with Web Crypto. Clear the record on completion, cancellation, expiry, logout or account change. Use the server's token binding across a full page navigation because in-memory session generations can reset on reload.
2. Navigate the same tab to the Google URL from the start response after verifying its HTTPS host and path. Add the distinct frontend callback to the approved SPA rewrite and OAuth client redirect allowlist. At callback entry, strip code/state from the address bar before analytics or subresource requests can record them. Use `no-store`, `no-referrer`, query-string redaction at ingress, and exclude the callback and API responses from service-worker caches. Keep provider tokens and the tab secret out of URLs, analytics and durable storage. Use `noopener` for any auxiliary links to avoid copying the tab's `sessionStorage`. Map denied or unsuccessful verification, session changes, timeouts and throttling to localized recovery states. For a stale or otherwise rejected proof, guide users to sign in again with the linked Google Account and restart without revealing the provider failure reason. Keep the tab in its original Loomora session and require a separate click to delete.
3. Prevent duplicate submits and ignore responses after a session change. Use the current 204-only success behavior. On success clear the matching account session and user-scoped caches across tabs, then route away. Preserve unrelated guest storage and any later account session. For a lost response, recheck the original session before trying again and avoid claiming deletion based solely on 401. Reconcile Profile, frontend API summary, and QA-004 disclosures with the approved launch behavior.

### Implementation regression plan

| Layer | Required coverage |
| --- | --- |
| Pest · request/auth | Anonymous, cookie-only, expired/revoked, other-user and same-user/different-token attempts. Wrong or absent tab verifier. Injected account ID cannot select a target. Validate both request shapes, ambiguity, 204-only deletion, existing correct/wrong/no-password behavior and linked-password precedence. Assert current JSON envelopes and no new login tokens. |
| Pest · provider and replay | Fake Google HTTP/JWKS and use locally signed ID-token fixtures. Cover invalid key/signature/algorithm, issuer, audience/authorized party, token times, state, nonce, PKCE rejection, absent and stale `auth_time`, skew and expiry boundaries, equal email with different `sub`, and changed email with matching `sub`. Cover Google cancellation/outage, canonical redirect, response redaction, CORS, rate limits and Retry-After. A sign-in exchange code cannot authorize deletion. Prove that a bare bearer, an account chooser, a verified email or a login callback cannot delete. |
| Pest · data and PostgreSQL races | Run with real Sanctum tokens and multiple database connections. Cover parallel verify, replacement during provider exchange, parallel deletes, password or linkage change, logout and issuance racing deletion, replay after success, and expiry between verification and final submit. Inject failure and verify rollback of proof, credentials, and owned data. On success verify every existing cascade, challenge cleanup, all-token and session revocation, and preservation of every other owner's data. Keep normal Google signup/sign-in, email verification and recovery regressions. |

| QA-009 · approved staging only | With synthetic accounts, establish exact frontend/backend SHAs. Confirm app eligibility, claim settings and registered callback. ## Planner decision

Keep Q23 open. Approve Option A with signed Google authentication within five minutes, the original Sanctum session, an explicit final confirmation, and the staged provider capability gate, or select Option C for initial public launch. If selecting C, decide the launch guidance for any existing Google-only users and whether already-linked Google sign-in stays available. If selecting B, explicitly accept mailbox assurance and require verified delivery in staging. Confirm the owner for app verification and claim/redirect settings, and accept or adjust the proposed limits and freshness windows. QA-004's disclosure work, Q25 owner verification and QA-009 release sign-off remain open.
