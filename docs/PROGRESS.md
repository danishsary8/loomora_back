### 2026-11-21 B-037 credential lifecycle across authentication boundaries

- **Base and evidence.** The isolated branch starts at the verified [B-036 PR #39 merge](https://github.com/danishsary8/loomora_back/pull/39), `24d4e7225fe212dfe73e41be9827e8509fe625ac`. B-036 recorded the baseline stale Google exchange and in-flight read results. Source review also found unsynchronized OAuth linking and reset-link issuance, a subject mismatch on email fallback, and registration separating account creation from bearer issuance. Verification for this change exercised the repaired paths with synthetic accounts.
- **Google grants.** Two nullable columns on the user hold the latest grant's digest and expiry. The existing row lock now covers grant creation, consumption, password reset and deletion. A newer callback replaces the pending grant. Reset clears it in the same commit as password save, bearer revocation and broker token consumption. Deletion removes the row. Exchange consumes the grant and writes the bearer together. A failed bearer insert rolls consumption back, so an unexpired grant can be retried. The additive upgrade keeps pre-existing users, bearers and recovery links. Legacy cached Google codes expire through their original cache TTL and receive the standard 422 on the upgraded API.
- **Recovery identity.** The Laravel broker retains its email-keyed table, 60-minute expiry and 60-second reissue throttle. Issuance and redemption lock the current user and give the broker that UUID. Deletion and new-account creation remove any row for the email under the account transaction. This prevents a reset row from crossing a deletion and registration handled by the new code. Historical rows under an email that was already reassigned before the upgrade carry no UUID and cannot be retrospectively attributed. The release cutover should allow any pre-cutover reset links to expire if account history cannot establish which user owned them.
- **Bearer policy.** Requests arriving with revoked bearers receive 401. Profile changes, survey submission, logout, verification resend and password-confirmed deletion recheck the account and bearer under the user lock. Reads authenticated before revocation may finish. Application resource routes such as to-dos, schedules and import retain authorization at request entry. An email already authorized or a response already committed can arrive after revocation. A subsequently presented bearer still has to authenticate.

| Operation | Lock and commit | External boundary |
|---|---|---|
| Email signup and password sign-in | Unique email insertion and first bearer commit together. Password sign-in checks the hash and issues the bearer under the user lock. | Registration mail follows commit. Delivery failure keeps the account and bearer. |
| Google callback and linking | Existing subject takes precedence over email. The callback locks the resolved UUID and rejects a mismatched subject or a UUID removed while it waited. Signup handles concurrent inserts with existing uniqueness constraints. Grant and link commit together. | Google is called before the database transaction. A still-valid provider response is resolved against the account state at its first database lookup. |
| Google exchange | An indexed digest lookup locks the matching user, checks expiry and commits consumption with bearer issuance. | The cache has no role in issuing or redeeming B-037 grants. Rate limiting still uses the configured cache. |
| Password recovery | Issuance, redemption and removal serialize on the user row. The broker's same-connection database writes participate in the transaction. | Reset mail is attempted after commit. The generic response survives delivery failure and the broker permits retry after its throttle. A superseded or deleted link is invalid even if delivery arrives later. |
| Logout and account deletion | Logout deletes the rechecked current bearer. Deletion rechecks the bearer and password, then commits all cleanup including cascades. | A successful delete returns empty 204. New requests with the old bearer return 401. |

The transaction prevents a callback from switching to a replacement once it has chosen a UUID. Extending revocation to provider flows that began before deletion would require a separate design, such as short-lived, identity-scoped deletion records with a retention and purge policy. That affects the immediate-deletion contract and needs planner approval. The callback rechecks state expiry after the provider call and any account-lock wait.

**Frontend and staging.** Existing client payloads, redirects, resource envelopes, account confirmations and 30-day bearer expiry apply. ### 2026-11-24: B-044 Lossless guest import investigation

- **Root cause:**
  1. `ImportRequest` limits `todos` to `max:500` (`Todo::MAX_PER_USER`) per request.
  2. `ImportRequest::checkLimits()` rejects an import if the user's live to-dos plus the new rows exceed 500.

### 2026-11-24: B-044 final review follow-up
- **Branch / PR:** same branch, [PR #48](https://github.com/danishsary8/loomora_back/pull/48). Not merged.
- **Ordering contract, corrected:** the earlier advice ("a successor with its predecessor or in an earlier chunk, subtasks with or after their parent") was valid for references but could fail near capacity. A successor sent before its predecessor counts as manual for that request, and its subtasks did too when they were sent right after it. A new test reproduced this: an account with 301 manual to-dos and a guest plan with 199 manual rows first got a 422 even though the final count is exactly 500. The contract is now in `openapi.yaml` (`POST /import`) and DECISIONS I9:
  1. **References (422 otherwise):** `parent_id` and `next_todo_id` must point at a row already on the account or in the same request. So a successor goes with its predecessor or earlier, and a subtask with its parent or later.
  2. **Capacity:** a successor counts as generated only once its predecessor is on the account or in the same request. Until then the successor and its subtasks count as manual for that request.
  3. **Safe order:**
     - Each repeat chain runs from the newest successor down to the original.
     - Each successor's subtasks go right after that successor's predecessor.
     - Other to-dos can go anywhere, each with its subtasks after it.
     - Cut the result into consecutive requests of at most 500.
  4. **Why the safe order never hits a false 422:** each chain has at most one successor waiting for its predecessor, and it is sent without its subtasks. That chain's original, a manual row, has not been sent yet. So the count during the import never exceeds the final manual count.
- **Real frontend (read-only, `loomora_front_v2` `origin/v2-rebuild` at `d18ca7d`, `src/lib/storage/saveGuestPlan.ts`):**

### 2026-11-25: B-045 Focus session label up to 200 characters

- **Why:** the owner decided (2026-11-25, spec S1 / D1) that Focus History keeps full to-do and schedule item titles, which can be 200 characters. The session `label` stopped at 120, so the frontend F-R3-10 snapshot was refused. Nothing may be truncated.
- **Changed:**
  - `FocusSession::MAX_LABEL_LENGTH` goes from 120 to 200. Validation (`max:` counts characters) and the error message follow it.
  - The original `create_focus_sessions_table` migration now states its length as the literal `120` instead of the constant, so a fresh database still builds the B-043 history before this change.
  - The new migration `2026_11_25_000000_widen_focus_session_label` widens `focus_sessions.label` to `varchar(200)`. Its `down()` refuses with a `RuntimeException` naming how many labels are longer than 120, so a rollback can never truncate. When every label fits, it narrows back to 120.
  - Contract: `docs/openapi.yaml` (`label` `maxLength: 200` and the bound text) and `docs/B-043-focus-session-design.md` (three places, marked "amended by B-045"). `docs/08-data-model.md` does not state the label length. Request and response shapes are unchanged, and existing labels are unchanged.

The existing bound message is now 200. The new `FocusSessionLabelMigrationTest` covers the column being 200 on PostgreSQL, rollback refusing with a 150-character label (label and column unchanged), and rollback then re-migration with a 120-character label.
