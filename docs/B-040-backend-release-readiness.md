- **Contract** — Registration, password login and Google exchange return `{token, expires_at, user}`. `GET /me` and ordinary individual resources use `{data: ...}`. Collections use `{data: [...]}`. Empty 204, 401, 403, 422, 429 and sanitized 500 behaviors remain documented. Special shapes such as schedule now/next are specified per endpoint.
- **Frontend copy** — B-039 compared backend blob `27ad5041baa54035503367419d46978f5723c2d5` with frontend snapshot `98a9b79c155a9c2bb23330245687bad4a6b859b7` and blob `ba9d006e21cc70118f23ccb39a08a36e53bbb7e3`. The frontend owner should copy the merged backend contract at the recorded SHA or its verified successor before QA-009.
- **Import** — The data model promises one import call with all-or-nothing behavior. The API commits each request, and the inspected frontend sends multiple ordered requests and retains the guest snapshot until they all succeed. A later failed chunk can leave an earlier one committed. B-039 observed successful ordered chunking and idempotent replay. The planner must decide whether to document per-request atomicity or require an atomic save of the whole guest plan. ### Finding — HTTP access-log query handling

**Medium, confirmed on the local baseline image.** Apache 2.4.71 uses a combined access log containing the full request line and Referer. `Dockerfile` leaves the inherited log format in place. The access log goes to stdout. One benign query marker on the local health request appeared in this stream. Apache therefore retains request query data at the container boundary, including on a credential-related route if present. The audit did not inspect hosted log content, access rights or retention. [Apache logging documentation](https://httpd.apache.org/docs/current/logs.html) · [Apache format directives](https://httpd.apache.org/docs/current/en/mod/mod_log_config.html)

Track a separate logging hardening task. Its source scope is `Dockerfile` and the Apache site/log configuration, with the operators responsible for Render/Vercel, proxy and application log streams. Use path-only request logging and omit or safely redact Referer values. Acceptance uses inert markers to verify method, sanitized path and status remain available while query and Referer data are excluded from emitted and collected logs. The owner must confirm minimum log access and retention and close Q25 with redacted evidence. Treat hosted logging readiness as blocked until logging controls and collection behavior are verified.

The blueprint uses this cheap check, so the cutover runbook also requires deep database health and a synthetic authenticated smoke on an approved environment. - **Upgrade from B-036.** B-038 verified the transition from `24d4e7225fe212dfe73e41be9827e8509fe625ac` to the B-037 merge using two real images and a populated disposable database. The new migration adds a nullable digest and expiry and a unique digest index. Eight original tables matched pre- and post-upgrade, including soft deletion and FKs. A pre-upgrade reset link worked for the verified continuous synthetic owner. These findings are specific to the disposable rehearsal and draft evidence. [B-038 PR #41](https://github.com/danishsary8/loomora_back/pull/41)
- **Cutover.** Confirm the deployed starting SHA and schema, restore backup/PITR to an isolated target, measure migration/index lock impact on realistic staging data, fence new credential traffic at all entrances, drain admitted handlers and stop old writers. Record the last possible old issuance. Allow the five-minute legacy Google grant lifetime to age out if old-route reachability is uncertain. If historical reset-row ownership cannot be established, keep reset issuance/redemption fenced through the 60-minute broker expiry plus clock margin. The email-keyed schema carries no historical user UUID.
- **Rollback.** Retain the additive migration. Prefer a compatible repaired image under a write fence, validate shallow/deep health and credential behavior, and reopen traffic only under the authorized procedure. Old credential handlers use a different grant store and weaker invalidation guarantees. Mixed-version serving and resuming older handlers can compromise the cutover. A historical restore can restore revoked credentials or deleted accounts. The database, application and security owners must approve any such recovery and document how to reconcile account and credential state.
- **Build and automation.** The exact archive built locally with locked Composer dependencies and a PHP 8.3 runtime. Composer and PHP image tags and OS packages can advance, so record resolved digests to identify the tested artifact and pin or mirror them if deterministic rebuilds are required. The entrypoint delegates process signals to Apache. The local container stopped gracefully on SIGWINCH with exit 0. Hosted shutdown timing and rollout overlap remain unverified. GitHub CI covers PHP 8.3, disposable PostgreSQL, Pint, Larastan, Pest, Docker boot and invalid-DB refusal. Local SQLite, explicit advisory scans, contract lint, deep health and paired staging supplement CI. The blueprint states the runtime and variable names. ## Q23 — deletion assurance and launch scope

Password recovery creates a reusable password through stored-mailbox access. The user subsequently signs in and explicitly confirms deletion with that password. Purpose-bound Google confirmation instead proves control of the linked Google identity for one deletion attempt and binds the proof to that action and session. Account recovery and deletion assurance are separate policy decisions. [Current behavior and design](B-034-google-account-deletion-design.md)

| Option | Experience and assurance | Existing evidence, requirements and scope |
|---|---|---|
| **A. Purpose-bound Google reauthentication** | Start from explicit deletion confirmation while signed in. Return from Google and complete the authorized action. Compare the linked subject and require a provider-verifiable recently authenticated session. A Google consent or account-selection prompt alone gives insufficient evidence of freshness. | Google sign-in and password-based transactional deletion exist. The proposed deletion proof, expiry, replay and session binding, provider validation and frontend initiation/return flow are new work across backend and frontend. First validate provider capability on approved staging. Requires cancellation, wrong-account, stale-proof, retry and rollback tests. |
| **B. Mailbox assurance** | Existing recovery uses a delivered reset link, establishes a reusable password and then requires fresh sign-in and deletion confirmation. A purpose-bound email option would issue a short-lived single-use deletion confirmation bound to the account and current session. Both rely on mailbox security and need a usable route for the user. | The recovery sequence uses existing endpoints, with atomic reset, grant/session revocation and local coverage. It needs planner approval of assurance, frontend disclosures/auth integration and a real delivered-link staged flow. Dedicated email confirmation would add backend token and transaction work, frontend landing/confirmation and provider delivery and failure testing. |
| **C. Restrict new Google-only signup for public launch** | Offer password signup in the public launch path while preserving a planner-approved route for existing Google-only accounts. Assurance for password-acquired accounts is the current password check. The scope decision must account for any existing Google-only users. | Current API permits Google signup. Enforcing restriction requires coordinated backend behavior, frontend signup affordances and messaging, compatibility with approved existing sign-in, and staged Google/credential edge cases. The concrete implementation depends on the chosen launch scope. |

Q23 remains open. Danish or the planner must choose the launch option, approve any follow-up scope and sign off after QA-009 proves the chosen behavior.
